# dev-loop — 아이디어에서 통과하는 테스트까지

대상: $ARGUMENTS

`goal` · `interview` · `sdd` · `tdd` 를 한 흐름으로 묶은 스킬이다.
개별 스킬을 각각 부를 수도 있지만, 이 스킬은 **순서와 게이트를 강제**한다.

```
  0. 준비        슬러그 정하고 상태 파일 만들기
       ↓
  1. GOAL        목표 한 문장 + 측정 가능한 성공 기준        → 게이트 A
       ↓
  2. INTERVIEW   요구사항 캐내기(discover) + 계획 심문(grill) → 게이트 B
       ↓
  3. SPEC        spec.md → plan.md → tasks.md              → 게이트 C
       ↓
  4. TDD         작업마다 RED → GREEN → REFACTOR            → 게이트 D
       ↓
  5. 마감        성공 기준 대조 + 회고
```

---

## 0. 준비

1. 사용자에게 짧은 슬러그를 받는다 (예: `attendance-bot`). 없으면 내가 제안하고 확인받는다.
2. 상태 파일을 만든다: `docs/dev-loop/<슬러그>/STATE.md`

```markdown
# dev-loop: <슬러그>
- 시작일: YYYY-MM-DD
- 현재 단계: 1-GOAL

| 단계 | 상태 | 산출물 | 게이트 |
| --- | --- | --- | --- |
| 1 GOAL | ☐ | | ☐ A |
| 2 INTERVIEW | ☐ | | ☐ B |
| 3 SPEC | ☐ | | ☐ C |
| 4 TDD | ☐ | | ☐ D |
| 5 마감 | ☐ | | |

## 결정 기록
| 날짜 | 결정 | 이유 |
| --- | --- | --- |

## 남은 질문
- [ ]
```

**중단했다 다시 시작할 때는 이 파일을 먼저 읽고 "현재 단계"부터 이어간다.**
사용자가 `/dev-loop <슬러그>` 로 부르면 상태 파일이 있는지 먼저 확인한다.

---

## 1. GOAL

`set-goal` 스킬의 절차를 따른다 → `docs/goals/<날짜>-<슬러그>.md`

### 🚧 게이트 A — 아래를 전부 만족해야 2단계로 간다
- [ ] 목표가 한 문장이다
- [ ] 성공 기준이 3개 이하이고, 전부 숫자 또는 관찰 가능한 행동이다
- [ ] 각 성공 기준에 측정 방법이 붙어 있다
- [ ] 비목표가 3개 이상이다

하나라도 비면 사용자에게 무엇이 비었는지 말하고 그것만 채운다. 통과했다고 넘겨짚지 않는다.

---

## 2. INTERVIEW

두 부분을 순서대로 한다.

**2-1. discover** — `interview` 스킬의 discover 모드.
한 번에 한 질문. 목표 문서에서 이미 답이 나온 항목은 건너뛴다.

**2-2. grill** — `interview` 스킬의 grill 모드.
1단계 목표와 2-1 요구사항을 대상으로 5축 심문. 시작 전 동의를 받는다.

> grill 을 건너뛰고 싶다고 하면 한 번만 권한다:
> "여기서 15분 쓰면 나중에 몇 시간을 아낍니다. 그래도 건너뛸까요?"
> 두 번째로 건너뛰겠다고 하면 그 결정을 STATE.md 결정 기록에 적고 넘어간다.

### 🚧 게이트 B
- [ ] 필수 요구사항(R-*)이 목록으로 정리됐다
- [ ] 범위 밖이 명시됐다
- [ ] grill 결과 "무너진 것(W-*)"에 각각 대응책이 붙었다
- [ ] 검증되지 않은 가정(A-*)에 각각 "확인 방법"이 적혔다

**무너진 항목의 대응책이 "목표를 바꾼다"면 1단계로 돌아간다.** 이건 실패가 아니라 이 파이프라인이 작동한 것이다.

---

## 3. SPEC

`sdd` 스킬을 따른다 → `docs/specs/<NNN>-<슬러그>/{spec.md, plan.md, tasks.md}`
(spec.md 는 `spec` 스킬의 템플릿과 점검표를 쓴다.)

1·2단계 산출물을 입력으로 쓴다:
- 목표의 성공 기준(SC) → 명세의 기능 요구사항(FR)
- 인터뷰 요구사항(R) → FR / 범위 밖
- 인터뷰 미해결 → `[NEEDS CLARIFICATION]`

### 🚧 게이트 C
- [ ] `[NEEDS CLARIFICATION]` 0개
- [ ] 모든 AC 가 Given/When/Then 형식이다
- [ ] 각 AC 에 담당 테스트가 지정됐다 (plan.md 검증 전략)
- [ ] 작업(T-*)이 10개 이하이고, 각각 완료 판정이 있다
- [ ] SC → FR → AC 사슬이 끊긴 곳이 없다

---

## 4. TDD

tasks.md 의 작업을 **위에서부터 하나씩**, 각 작업을 `tdd` 스킬의 사이클로 처리한다.

작업 하나가 끝날 때마다:
1. tasks.md 상태 ☑
2. STATE.md 갱신
3. 전체 테스트 실행 → 초록 확인
4. 다음 작업으로

구현 중 명세가 틀렸다는 게 드러나면:
- 코드를 고치기 전에 **spec.md 를 먼저 고친다**
- 변경 이유를 STATE.md 결정 기록에 남긴다
- 그 변경이 성공 기준을 흔들면 1단계로 돌아간다

### 🚧 게이트 D
- [ ] 모든 작업 ☑
- [ ] 전체 테스트 초록, skip 0개
- [ ] 모든 AC 에 실제로 통과하는 테스트가 있다
- [ ] 실패를 실제로 본 적 없는 테스트가 없다

---

## 5. 마감

목표 문서의 성공 기준을 하나씩 대조한다.

```markdown
## 마감 점검
| 성공 기준 | 측정 방법 | 실제 결과 | 판정 |
| --- | --- | --- | --- |
| SC-1 | | | 달성 / 미달 / 측정불가 |

## 회고
- 게이트 중 가장 오래 걸린 곳:
- grill 에서 나온 지적 중 실제로 맞았던 것:
- 명세가 바뀐 횟수와 이유:
- 다음에 다르게 할 것:
```

`docs/dev-loop/<슬러그>/CLOSE.md` 로 저장하고, STATE.md 를 `완료` 로 바꾼다.

**"측정불가" 가 나오면 성공 기준이 처음부터 측정 가능하지 않았던 것이다.** 회고에 적는다.

---

## 이 스킬의 규칙

1. **게이트를 눈으로 확인한다.** 체크리스트를 사용자에게 보여주고 통과를 선언한다. 조용히 넘어가지 않는다.
2. **되돌아가는 건 정상이다.** 3단계에서 목표가 틀린 걸 알면 1단계로 돌아간다. 창피한 일이 아니라 이 구조를 쓰는 이유다.
3. **단계를 건너뛰자는 요청은 한 번만 말린다.** 두 번째엔 STATE.md 에 기록하고 따른다.
4. **각 단계가 끝날 때마다 멈추고 확인받는다.** 5단계를 한 번에 쏟아내지 않는다.
5. **작은 일에는 쓰지 않는다.** 오타 수정, 한 줄 변경에 이 파이프라인을 돌리자고 하면 과하다고 말하고 바로 처리한다.

## 빠른 경로

이미 확실한 단계가 있으면 그 단계 산출물만 확인하고 건너뛴다:

| 상황 | 시작 단계 |
| --- | --- |
| 목표 문서가 이미 있다 | 2 |
| 요구사항이 확정돼 있다 | 3 |
| 명세와 작업 목록이 있다 | 4 |
| 계획이 미덥지 않다 | 2 의 grill 만 |
