# handoff — 작업 인수인계

입력: $ARGUMENTS

## 모드

| 입력 | 모드 | 하는 일 |
| --- | --- | --- |
| `/handoff` | **write** | 지금 상태를 문서로 남기고 중단한다 |
| `/handoff resume` | **resume** | 최근 문서를 읽고 그 지점부터 이어간다 |

받는 사람은 **다음 주의 나 자신**이라고 가정한다. 그 사람은 지금 내가 아는 걸
하나도 기억하지 못한다. "대충 알 것"이라고 넘긴 부분에서 정확히 막힌다.

---

## 모드 1: write — 중단하며 넘기기

### 절차

**1. 사실을 모은다.** 기억이 아니라 실제 상태를 읽는다.

```bash
git status --short
git log --oneline -5
git diff --stat
```

- 커밋 안 된 변경이 있는가
- 브랜치가 어디인가, 원격과 차이가 있는가
- 테스트가 지금 통과하는가 — **모르면 돌려본다.** 추측해서 적지 않는다

**2. 다음 한 줄을 정한다.** 이 문서에서 가장 중요한 항목이다.

> ❌ "인증 부분 마저 하기"
> ⭕ "`auth.py:42` 의 `verify_token` 이 만료된 토큰에서 None 을 반환함. 예외를 던지도록 바꾸고 `test_expired_token` 을 통과시킬 것."

**파일과 줄 번호가 없으면 다시 쓴다.**

**3. 막힌 것을 솔직하게 적는다.** 여기서 체면을 차리면 다음 사람이 같은 벽에 부딪힌다.
시도한 것과 그 결과를 함께 적는다 — 안 되는 방법을 아는 것도 자산이다.

**4. 함정을 적는다.** 건드리면 안 되는 것, 이유 있는 이상한 코드, 되돌리면 안 되는 변경.

### 산출물

`docs/handoff/<날짜>-<슬러그>.md`

```markdown
# 인수인계: <작업 이름>
- 작성: YYYY-MM-DD HH:MM
- 브랜치 / 마지막 커밋: <이름> / <해시 한 줄>

## 한 줄 요약
<지금 무슨 일을 하는 중인가.>

## 다음에 할 일 (딱 하나)
<파일:줄 을 포함해서 구체적으로. 바로 손댈 수 있게.>

## 지금 상태
| 항목 | 상태 |
| --- | --- |
| 커밋 안 된 변경 | 있음 / 없음 — <무엇> |
| 테스트 | ✅ 전부 통과 / ❌ N개 실패 (<어느 것>) / ⏭ 안 돌려봄 |
| 실행 되는가 | 됨 / 안 됨 — <증상> |

## 여기까지 한 것
- ✅ <끝난 것>
- 🔨 <하다 만 것 — 어디까지 했는지 파일:줄>

## 막힌 것
- **증상**: <무엇이 안 되는가>
- **시도한 것**: <했는데 안 된 방법들>
- **다음 가설**: <아직 안 해본 것>

## 함정 (건드리기 전에 읽을 것)
- ⚠️ <이유 있는 이상한 코드 / 되돌리면 안 되는 것>

## 재현 명령
바로 복붙할 수 있게 적는다.

    <프로젝트 실행 명령>
    <테스트 명령>
    <문제 재현 명령>

## 열어둔 질문
- [ ] <사람에게 물어야 할 것>
```

### 마무리

문서를 쓴 뒤 사용자에게 묻는다:
> "커밋하고 마무리할까요?" — 커밋 안 된 변경이 있을 때만.

**사용자 확인 없이 커밋·푸시하지 않는다.**

---

## 모드 2: resume — 이어서 시작하기

**1. 최근 인수인계 문서를 찾는다.** `docs/handoff/` 에서 가장 최근 것.
여러 개면 목록을 보여주고 어느 것인지 묻는다.

**2. 문서가 아직 맞는지 검증한다.** 이게 핵심이다. 문서는 낡는다.

| 문서가 말하는 것 | 실제로 확인 |
| --- | --- |
| 브랜치 / 마지막 커밋 | `git log --oneline -3` 과 일치하는가 |
| 커밋 안 된 변경 | `git status` 와 일치하는가 |
| 테스트 상태 | **직접 돌려본다** |

**어긋난 게 있으면 먼저 사용자에게 알린다.** 그 사이에 다른 작업이 있었다는 뜻이다.

**3. 요약해서 보고한다.**

```
📄 <문서 이름> (N일 전)
   작업: <한 줄 요약>
   다음: <다음에 할 일>

🔍 현재 상태 확인
   브랜치: 문서와 일치 ✅ / 다름 ⚠️
   테스트: <실제 실행 결과>

▶ 이어서 진행할까요?
```

**4. 확인받고 시작한다.** 사용자가 "응" 하면 "다음에 할 일" 한 줄부터 손댄다.

---

## 하지 말 것

- 상태를 **기억으로** 적기 — `git status` 와 테스트를 실제로 돌려서 적는다
- "다음: 마저 하기" 같은 다음 할 일 — 파일·줄 번호가 없으면 쓸모없다
- 막힌 것을 안 적거나 축소해서 적기
- resume 에서 문서를 검증 없이 믿기 — 그 사이에 코드가 바뀌었을 수 있다
- 확인 없이 커밋·푸시하기

## 다른 스킬과의 관계

- `dev-loop` 의 `STATE.md` 는 **파이프라인 단계**를 추적한다 (지금 몇 단계인가)
- `handoff` 는 **작업 상태**를 넘긴다 (지금 코드가 어떤 상태인가)
- dev-loop 진행 중에 중단한다면 둘 다 남기는 게 좋다. STATE.md 는 단계, handoff 는 손에 쥔 것.
