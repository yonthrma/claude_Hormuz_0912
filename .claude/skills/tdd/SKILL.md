# tdd — 테스트 주도 개발

대상: $ARGUMENTS

## 사이클

```
🔴 RED     실패하는 테스트를 쓴다 → 실행한다 → 실패를 눈으로 확인한다
🟢 GREEN   통과시키는 가장 단순한 코드를 쓴다 → 실행한다 → 통과를 확인한다
🔵 REFACTOR 테스트는 그대로 두고 코드를 정리한다 → 다시 실행한다 → 여전히 통과
```

한 사이클 = 테스트 하나. 사이클을 건너뛰지 않는다.

---

## 시작 전

1. **테스트 러너를 찾는다.** `package.json`, `pyproject.toml`, `pytest.ini`, `go.mod`, `Cargo.toml` 등을 보고 이 프로젝트가 이미 쓰는 도구를 쓴다. 새 프레임워크를 임의로 들여오지 않는다.
2. **기존 테스트를 한 번 돌린다.** 시작부터 깨져 있으면 사용자에게 알리고, 내 변경 때문이 아님을 분명히 한다.
3. **무엇을 테스트할지 목록을 만든다.** 명세(`/sdd`)가 있으면 AC를 그대로 가져온다.

```markdown
## 테스트 목록
- [ ] 정상: <가장 단순한 성공 경로>
- [ ] 경계: <빈 값 / 0 / 최대값>
- [ ] 실패: <잘못된 입력이 어떻게 실패해야 하는가>
```

위에서부터 하나씩 처리한다. **가장 단순한 것부터.**

---

## 🔴 RED

- 목록에서 **하나만** 골라 테스트를 쓴다.
- 테스트 이름은 문장으로 쓴다: `test_빈_장바구니의_합계는_0원이다`
- 하나의 테스트는 하나만 검증한다. `assert`가 5개 붙으면 테스트를 쪼갠다.
- **테스트를 실행하고 실패 출력을 사용자에게 그대로 보여준다.**

> 이게 이 스킬의 핵심이다. 실패를 보지 않고 넘어가면 그 테스트가 진짜로
> 무언가를 검증하는지 알 수 없다. "실패할 겁니다"라고 말만 하고 넘어가지 않는다.

실패 이유를 확인한다:
- ✅ 좋은 실패: 기능이 없어서 / 결과가 기대와 달라서
- ❌ 나쁜 실패: 오타, import 오류, 테스트 파일을 못 찾음 → 이건 고치고 다시 RED

---

## 🟢 GREEN

- **통과시키는 가장 단순한 코드**를 쓴다. 미래를 위한 일반화는 지금 하지 않는다.
- 아직 없는 케이스를 미리 처리하지 않는다. 그 케이스는 다음 사이클의 테스트가 요구할 것이다.
- 실행해서 **통과를 확인하고 출력을 보여준다.**
- 다른 테스트가 깨졌으면 지금 멈추고 고친다. 깨진 채로 다음 사이클로 가지 않는다.

---

## 🔵 REFACTOR

- 중복 제거, 이름 개선, 함수 분리.
- **테스트 코드는 건드리지 않는다.** (테스트 자체의 중복 정리는 별도 사이클로)
- 정리 후 다시 전체 테스트 실행 → 여전히 초록.
- 정리할 게 없으면 건너뛴다. 억지로 리팩터하지 않는다.

사이클이 끝나면 목록의 그 항목을 ☑ 로 바꾸고, 다음 항목으로 간다.

---

## 절대 금지

| 금지 | 왜 |
| --- | --- |
| 테스트를 통과시키려고 **테스트를 수정**하기 | 검증이 사라진다. 구현이 틀린 건지 테스트가 틀린 건지 먼저 판단하고, 테스트가 틀렸다면 그 이유를 사용자에게 말한 뒤 고친다 |
| 실패를 실제로 실행해보지 않고 GREEN 으로 넘어가기 | 검증하지 않는 테스트가 생긴다 |
| 테스트 여러 개를 한꺼번에 쓰고 한꺼번에 통과시키기 | 어느 코드가 어느 테스트를 통과시켰는지 모른다 |
| 통과 안 되는 테스트를 `skip` / 주석 처리 | 문제를 숨기는 것이다. 사용자에게 보고한다 |
| 구현부터 쓰고 테스트를 나중에 맞추기 | 그건 TDD 가 아니라 테스트 후행 작성이다 |
| 테스트에서 검증 대상 로직을 다시 구현하기 | 같은 버그가 양쪽에 생긴다. 기대값은 손으로 계산한 리터럴로 쓴다 |

## 보고 형식

사이클마다 이렇게 보고한다:

```
🔴 RED   test_빈_장바구니의_합계는_0원이다
         → 실패 확인: AttributeError: 'Cart' has no attribute 'total'
🟢 GREEN Cart.total 추가 (5줄) → 1 passed
🔵 REFACTOR 건너뜀 (정리할 것 없음)
   진행: 1/4
```

---

## 테스트가 어려울 때

테스트를 쓰기가 유난히 힘들면 그건 테스트의 문제가 아니라 **설계 신호**다.
사용자에게 알린다:

- 준비 코드가 20줄 넘는다 → 의존성이 너무 많다
- 시간·랜덤·네트워크 때문에 못 쓴다 → 그것들을 인자로 주입할 수 있는지 본다
- 무엇을 검증할지 모르겠다 → 요구사항이 흐릿한 것. `/interview` 나 `/sdd` 로 돌아간다

## 완료 체크리스트

- [ ] 테스트 목록의 모든 항목이 ☑
- [ ] 모든 테스트가 한 번은 실패하는 걸 실제로 봤다
- [ ] 전체 테스트가 초록이다 (skip 없음)
- [ ] 명세가 있다면 모든 AC 에 대응하는 테스트가 있다
- [ ] 테스트를 통과시키려고 테스트를 고친 적이 없다
