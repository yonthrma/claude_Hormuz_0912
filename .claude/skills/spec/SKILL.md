# spec — 명세서 작성 & 점검

대상: $ARGUMENTS

## 모드

| 입력 | 모드 | 하는 일 |
| --- | --- | --- |
| `/spec <기능>` | **write** | 명세서를 새로 쓴다 |
| `/spec review <파일>` | **review** | 이미 있는 명세를 점검하고 구멍을 지적한다 |

`sdd` 스킬과의 관계: `sdd` 는 `명세 → 계획 → 작업 → 구현` 전체를 게이트로 묶는다.
이 스킬은 그중 **명세 문서 하나**만 다룬다. 계획·작업까지 필요하면 `/sdd` 를 쓴다.

---

## 철칙 — 명세에 쓰지 않는 것

명세는 **무엇을·왜**만 적는다. 아래가 나오면 잘못 쓴 것이다.

| 금지 | 왜 | 대신 |
| --- | --- | --- |
| 라이브러리·프레임워크 이름 | 명세가 특정 구현에 묶인다 | "CSV 파일을 읽는다" |
| 함수·클래스·파일 이름 | 설계는 계획 단계의 일이다 | 동작으로 서술 |
| DB 스키마, API 엔드포인트 | 같음 | "무엇을 저장해야 하는가"만 |
| "~를 사용해서" | 방법이지 요구사항이 아니다 | "~할 수 있어야 한다" |

예외: 사용자가 "반드시 X를 써야 한다"고 못박은 경우. 이때는 **제약** 항목에 적고, 왜 그런지도 적는다.

## 모드 1: write — 명세 쓰기

### 절차

**1. 재료를 모은다.** 이미 있는 걸 먼저 찾는다.
- `docs/goals/` 에 목표 문서가 있는가 → 성공 기준을 요구사항의 뿌리로 쓴다
- `docs/interviews/` 에 인터뷰 기록이 있는가 → 요구사항·범위 밖을 가져온다
- 없으면 그대로 진행한다. **없다고 인터뷰를 강요하지 않는다.**

**2. 초안을 쓴다.** 모르는 건 지어내지 말고 `[NEEDS CLARIFICATION]` 으로 남긴다.

**3. 자체 점검을 돌린다.** (아래 review 체크리스트를 그대로 적용)

**4. 미해결 질문을 사용자에게 낸다.** 한 번에 하나씩. 3개를 넘으면
   "인터뷰가 낫겠다"고 제안하고 `/interview` 로 넘긴다.

### 저장 위치

- 단독으로 쓸 때: `docs/specs/<NNN>-<슬러그>.md`
- `/sdd` 파이프라인 안에서: `docs/specs/<NNN>-<슬러그>/spec.md`

NNN 은 001부터. 기존 폴더를 보고 다음 번호를 쓴다.

### 템플릿

```markdown
# 명세: <기능 이름>

- ID: <NNN>-<슬러그>
- 작성일: YYYY-MM-DD
- 상태: draft | ready | implemented
- 관련 문서: <목표/인터뷰 문서 링크, 있으면>

## 배경
<왜 이게 필요한가. 2~3줄. 이 기능이 없으면 누가 무엇을 못 하는가.>

## 사용자 시나리오
주인공: <구체적인 한 사람. "사용자" 말고 "출석을 부르는 강사 김OO">

1. 그는 ___ 하려고 한다
2. 그래서 ___ 를 한다
3. 시스템은 ___ 를 보여준다
4. 그는 ___ 를 얻고 끝낸다

## 기능 요구사항
| ID | 요구사항 | 우선순위 | 출처 |
| --- | --- | --- | --- |
| FR-1 | 시스템은 ___ 해야 한다 | 필수 | SC-1 |
| FR-2 | | 필수 | R-2 |
| FR-3 | | 선택 | |

각 요구사항은 **한 문장, 하나의 동작**. "그리고"가 들어가면 쪼갠다.

## 수용 기준 (Given / When / Then)
FR 마다 최소 두 개 — 성공 경로 하나, 실패 경로 하나.

- **AC-1** (FR-1, 성공)
  - Given: <시작 상태>
  - When: <행동>
  - Then: <관찰 가능한 결과>

- **AC-2** (FR-1, 실패)
  - Given: <시작 상태>
  - When: <잘못된 입력 또는 예외 상황>
  - Then: <어떻게 실패해야 하는가 — 조용히 죽으면 안 된다>

## 비기능 요구사항
| 항목 | 기준 | 측정 방법 |
| --- | --- | --- |
| 성능 | | |
| 데이터 규모 | | |
| 오류 처리 | | |
| 보안 / 개인정보 | | |
| 접근성·환경 | | |

빈 칸은 "해당 없음"이라고 적는다. **비워두지 않는다** — 빈 칸은 "안 물어봤다"와 구별되지 않는다.

## 범위 밖
- 이번에 하지 않는다: <...>
- 이번에 하지 않는다: <...>

## 제약
<반드시 써야 하는 기술·환경이 있다면 여기에. 이유도 함께.>

## 미해결 질문
- [ ] [NEEDS CLARIFICATION] <이 답이 없으면 구현할 수 없는 질문>
```

## 모드 2: review — 명세 점검

기존 명세를 읽고 아래를 하나씩 확인한다. **통과 항목도 소리 내어 확인한다.**

### 점검표

| # | 확인 | 걸리면 |
| --- | --- | --- |
| 1 | 구현 세부사항(라이브러리·함수·스키마)이 섞였는가 | 해당 문장을 인용하고 동작 서술로 바꿔 제안 |
| 2 | 주인공이 "사용자"처럼 뭉뚱그려졌는가 | 구체적인 한 사람으로 좁히라고 요구 |
| 3 | FR 중 "그리고"로 두 동작이 붙은 게 있는가 | 쪼갠다 |
| 4 | AC 없는 FR 이 있는가 | 그 FR 은 테스트할 수 없다. AC 를 만든다 |
| 5 | 실패 경로 AC 가 하나도 없는 FR 이 있는가 | 잘못된 입력에서 어떻게 되는지 묻는다 |
| 6 | AC 의 Then 이 관찰 불가능한가 ("잘 처리된다") | 무엇을 보면 아는지 묻는다 |
| 7 | 비기능 표에 빈 칸이 있는가 | "해당 없음"이라도 채운다 |
| 8 | 범위 밖이 비었는가 | 최소 2개를 받아낸다 |
| 9 | `[NEEDS CLARIFICATION]` 이 남았는가 | 하나씩 사용자에게 묻는다 |
| 10 | 요구사항 중 출처(목표 SC / 인터뷰 R)가 없는 게 있는가 | 왜 필요한지 묻는다. 답이 약하면 뺄 후보 |

### 점검 결과 형식

```markdown
## 명세 점검: <파일>

| # | 항목 | 판정 |
| --- | --- | --- |
| 1 | 구현 세부사항 없음 | 통과 / 걸림 |
| ... | | |

### 고쳐야 할 것
- [ ] <위치>: <무엇이 문제인가> → <어떻게 고치나>

### 물어봐야 할 것
- [ ] <질문>

### 판정
- [ ] ready — 이대로 계획 단계로
- [ ] 수정 필요 — 위 항목 처리 후 재점검
```

## 다음 단계 안내

명세가 `ready` 가 되면 사용자에게 다음을 제안한다:

| 상황 | 다음 |
| --- | --- |
| 어떻게 만들지 정해야 한다 | `/sdd` — plan.md, tasks.md 로 이어간다 |
| 바로 코드로 간다 | `/tdd` — AC 를 테스트 목록으로 옮긴다 |
| 요구사항 자체가 흔들린다 | `/interview` 또는 `/interview grill` |
| 왜 만드는지가 흐리다 | `/set-goal` |

## 하지 말 것

- `[NEEDS CLARIFICATION]` 을 내 추측으로 조용히 채우기 — 추측했으면 반드시 "제가 ___로 가정했습니다"라고 밝힌다
- 명세를 다 쓰고 곧바로 구현 시작하기 — 이 스킬은 문서에서 끝난다
- 사용자가 한 말에 없는 요구사항을 "있으면 좋을 것 같아서" 넣기
- 미해결 질문 5개를 한꺼번에 쏟아내기 — 하나씩 묻는다
