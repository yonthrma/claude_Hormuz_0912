# set-goal — 목표 확정 스킬

대상: $ARGUMENTS

## 이 스킬이 하는 일

"좋은 앱을 만들고 싶다" 같은 말을 **측정 가능한 한 문장 + 검증 가능한 성공 기준**으로 바꾼다.
목표가 흐릿하면 그 뒤의 명세도 테스트도 전부 흐릿해진다. 여기가 첫 관문이다.

## 절차

한 단계씩 진행한다. 사용자가 답하기 전에 다음 단계로 넘어가지 않는다.

### 1단계 — 한 문장으로 좁히기
사용자에게 목표를 한 문장으로 말하게 한다. 사용자가 길게 말하면 내가 한 문장으로 압축해서
"이 문장이 맞습니까?"라고 되묻는다.

형식: `[누가] [무엇을] 할 수 있게 만든다. [언제까지].`

### 2단계 — 왜 지금인가
왜 이걸 지금 하는지 한 줄. 답이 "그냥"이면 목표를 접거나 범위를 줄이라고 말한다.

### 3단계 — 성공 기준 (최대 3개)
각 기준은 **숫자 또는 관찰 가능한 행동**이어야 한다.

다음 표현이 나오면 그대로 두지 말고 되묻는다:

| 거부할 표현 | 되물을 질문 |
| --- | --- |
| 사용하기 쉽게 | 누가, 몇 초 안에, 무엇을 끝내면 쉬운 겁니까? |
| 빠르게 | 몇 ms/몇 초 이하입니까? 무엇을 기준으로 잽니까? |
| 안정적으로 | 어떤 입력에서 안 죽으면 됩니까? 실패율 몇 % 이하? |
| 예쁘게 | 무엇과 비교해서 판단합니까? 판단하는 사람은 누구입니까? |
| 많은 사람이 | 몇 명입니까? 어디서 셉니까? |

### 4단계 — 비목표 (Non-goals)
"이번에 안 하는 것"을 최소 3개 적는다. 비목표가 없으면 범위가 정해지지 않은 것이다.

### 5단계 — 제약
기한 / 쓸 수 있는 시간 / 기술 스택 / 절대 건드리면 안 되는 것.

### 6단계 — 완료의 정의(DoD)
"이게 되면 끝"이라고 말할 수 있는 관찰 가능한 상태. 성공 기준과 다르다.
성공 기준은 "잘 됐는가", DoD는 "끝났는가"다.

## 산출물

`docs/goals/<날짜>-<슬러그>.md` 로 저장한다.

```markdown
# 목표: <한 문장>

- 작성일: YYYY-MM-DD
- 상태: draft | confirmed | done | dropped

## 왜 지금
<한 줄>

## 성공 기준
- [ ] SC-1: <측정 가능한 문장 + 측정 방법>
- [ ] SC-2:
- [ ] SC-3:

## 비목표
- 이번에 하지 않는다: <...>
- 이번에 하지 않는다: <...>
- 이번에 하지 않는다: <...>

## 제약
| 항목 | 내용 |
| --- | --- |
| 기한 | |
| 투입 시간 | |
| 기술/환경 | |
| 건드리지 않을 것 | |

## 완료의 정의 (DoD)
<이 상태가 되면 끝났다고 선언한다>

## 첫 번째 검증 단계
<하루 안에 끝나고, 목표가 말이 되는지 확인할 수 있는 가장 작은 행동>

## 미해결
- [ ] <아직 모르는 것>
```

## 규칙

1. 성공 기준이 3개를 넘으면 목표가 두 개 이상 섞여 있는 것이다. 쪼개자고 제안한다.
2. 측정 방법 없는 숫자는 숫자가 아니다. "3초 이내"에는 반드시 "무엇을 기준으로 재는가"가 붙는다.
3. 사용자가 "일단 만들면서 정하자"고 하면 한 번은 말린다. 두 번 말하면 그 결정을 문서에 적고 진행한다.
4. 목표 문서를 다 쓰면 **곧바로 구현으로 넘어가지 않는다.** 다음 단계를 제안한다:
   - 요구사항이 흐릿하다 → `/interview`
   - 목표는 섰는데 계획이 미덥지 않다 → `/interview grill`
   - 무엇을 만들지는 분명하다 → `/sdd`

## 완료 체크리스트

- [ ] 목표가 한 문장이다
- [ ] 성공 기준이 전부 숫자 또는 관찰 가능한 행동이다
- [ ] 각 성공 기준에 측정 방법이 있다
- [ ] 비목표가 3개 이상이다
- [ ] DoD를 읽고 "끝났는지" 논쟁이 안 생긴다
- [ ] 파일이 `docs/goals/` 에 저장됐다
