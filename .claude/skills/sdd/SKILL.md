# sdd — 명세 우선 개발

대상: $ARGUMENTS

## 원칙

**코드는 명세의 번역물이다.** 명세가 애매하면 코드도 애매하다.
그래서 이 스킬은 순서를 강제한다:

```
spec.md  (무엇을·왜)  →  plan.md  (어떻게)  →  tasks.md  (어떤 순서로)  →  구현
   ↑                                                                      │
   └──────────── 구현 중 명세가 틀린 걸 발견하면 여기로 돌아온다 ─────────────┘
```

산출물은 전부 `docs/specs/<NNN>-<슬러그>/` 아래에 둔다. (NNN = 001, 002, ...)

---

## 1단계 — spec.md (무엇을, 왜)

명세 하나만 따로 다루고 싶으면 `/spec` 스킬을 쓴다. 점검표(`/spec review`)도 거기 있다.
이 단계는 그 결과물을 `docs/specs/<NNN>-<슬러그>/spec.md` 로 받는다.

**구현 방법을 쓰지 않는다.** 라이브러리 이름, 함수 이름, 파일 구조가 spec에 나오면 잘못 쓴 것이다.

```markdown
# 명세: <기능 이름>
- ID: 001-<슬러그> / 작성일 / 상태: draft | ready | implemented

## 배경
<왜 이게 필요한가. 2~3줄. 연결된 목표 문서가 있으면 링크.>

## 사용자 시나리오
주인공: <구체적인 한 사람>
1. 그는 ___ 하려고 한다
2. 그래서 ___ 를 한다
3. 시스템은 ___ 를 보여준다
4. 그는 ___ 를 얻고 끝낸다

## 기능 요구사항
| ID | 요구사항 | 우선순위 |
| --- | --- | --- |
| FR-1 | 시스템은 ___ 해야 한다 | 필수 |
| FR-2 | | 필수 |
| FR-3 | | 선택 |

## 수용 기준 (Given/When/Then)
각 FR마다 최소 하나. 이게 나중에 그대로 테스트가 된다.

- AC-1 (FR-1)
  - Given: <시작 상태>
  - When: <행동>
  - Then: <관찰 가능한 결과>

- AC-2 (FR-1, 실패 경로)
  - Given: / When: <잘못된 입력> / Then: <어떻게 실패해야 하는가>

## 비기능 요구사항
| 항목 | 기준 |
| --- | --- |
| 성능 | |
| 데이터 규모 | |
| 오류 처리 | |
| 보안/개인정보 | |

## 범위 밖
- 

## 미해결 질문
- [ ] [NEEDS CLARIFICATION] <답이 없으면 구현할 수 없는 질문>
```

### 게이트 ①
`[NEEDS CLARIFICATION]` 이 하나라도 남아 있으면 **plan.md 로 넘어가지 않는다.**
사용자에게 그 질문들을 한 번에 하나씩 묻는다. (인터뷰가 길어질 것 같으면 `/interview` 로 넘긴다.)

---

## 2단계 — plan.md (어떻게)

```markdown
# 계획: <기능 이름>

## 접근 방식
<두세 문단. 왜 이 방식인가.>

## 검토한 대안
| 대안 | 장점 | 단점 | 채택? |
| --- | --- | --- | --- |

## 건드리는 것
| 파일/모듈 | 신규? | 무엇을 |
| --- | --- | --- |

## 데이터 모양
<입력/출력/저장 구조. 실제 예시 값으로.>

## 위험
| 위험 | 가능성 | 대응 |
| --- | --- | --- |

## 검증 전략
- 단위 테스트로 덮을 것:
- 손으로 확인할 것:
- 각 AC를 어떤 테스트가 책임지는가:
  - AC-1 → <테스트 이름>
```

### 게이트 ②
**모든 AC가 최소 하나의 테스트에 매핑돼야 한다.** 매핑되지 않은 AC가 있으면 tasks.md 로 못 간다.

---

## 3단계 — tasks.md (어떤 순서로)

작업 하나는 **한 번에 완결되고 검증 가능한 크기**여야 한다. 30분~2시간이 기준.

```markdown
# 작업: <기능 이름>

| # | 작업 | 선행 | 완료 판정 | 상태 |
| --- | --- | --- | --- | --- |
| T-1 | | - | <이게 되면 끝> | ☐ |
| T-2 | | T-1 | | ☐ |

## 작업 순서 근거
<왜 이 순서인가. 무엇이 무엇을 막는가.>
```

각 작업 완료 판정에 "테스트가 통과한다"가 들어가면 그 작업은 `/tdd` 로 실행한다.

### 게이트 ③
작업이 10개를 넘으면 기능이 너무 크다. 명세를 둘로 쪼개자고 제안한다.

---

## 4단계 — 구현

- **한 번에 한 작업.** T-1 끝나고 상태를 ☑ 로 바꾼 다음 T-2 로 간다.
- 구현 중 명세와 다른 걸 하게 되면 **코드를 고치기 전에 spec.md 를 고친다.** 그리고 왜 바뀌었는지 한 줄 남긴다.
- 작업 끝날 때마다 해당 AC가 실제로 만족되는지 확인한다.

---

## 추적 규칙

모든 것은 ID로 이어져야 한다:

```
목표 SC-1  →  FR-2  →  AC-3  →  테스트 test_xxx  →  커밋
```

이 사슬이 끊긴 코드는 "왜 있는지 모르는 코드"다. 발견하면 사용자에게 알린다.

---

## 하지 말 것

- spec.md 없이 코드 쓰기
- spec.md 에 구현 세부사항(라이브러리·함수명) 넣기
- `[NEEDS CLARIFICATION]` 을 내 추측으로 채우기 — 추측했으면 반드시 "제가 ___로 가정했습니다"라고 밝힌다
- 세 문서를 한 번에 쏟아내고 확인 안 받기 — 문서 하나 끝날 때마다 확인받는다
- 명세와 다르게 구현해놓고 명세를 나중에 맞추기
